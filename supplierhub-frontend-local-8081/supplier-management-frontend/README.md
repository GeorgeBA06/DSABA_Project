# SupplierHub — frontend, интеграционная редакция Stage 2

**Состояние:** все **97 HTTP-операций** замороженного backend Stage 4 сопоставлены с UI, но запуск приложения с настоящими зависимостями и PostgreSQL **не проверен**. Статическое покрытие маршрутов не является доказательством исполнения всего приложения end-to-end.

## Технологии и оформление

React 19 + TypeScript + Vite, REST/JSON; единый тёмно-синий sidebar, светлая рабочая область, синие акценты, русские статусы, компактные таблицы, BYN без НДС. Нет выдуманных данных и дополнительной бизнес-логики на клиенте.

## Что поддерживается

- Авторизация: вход, `/auth/me`, обновление access/refresh, выход, смена своего пароля; восстановление сессии после обновления вкладки.
- Поставщики: реестр, карточка, создание/редактирование, ассортимент поставщика, заявки на смену статуса и независимое согласование.
- Каталог: товары, категории, единицы измерения; активность товара (руководитель).
- Договоры: создание, версии, отправка/решение, изменение версии, прекращение.
- Заказы: черновик, переработка отклонённого документа, увеличение количества, перенос срока, согласование, закрытие/возобновление.
- Исполнение: поступление, подтверждение, приёмка, частичная проверка, возврат, создание/согласование исправлений.
- Взаимодействия/претензии: фиксация общения, создание/отправка претензии, урегулирование; независимое решение для неполного удовлетворения.
- Аналитика: рейтинг и исходные показатели, экспертные оценки, расчёт рейтинга, реестр отчёта и экспорт XLSX.
- Администрирование: пользователи, создание, блокировка/разблокировка, назначение/отзыв ролей, сброс пароля, аудит.

Условия видимости кнопок учитывают роли и известные состояния. Полномочия окончательно проверяются сервисами backend.

## Важно: совместимая версия backend

В архиве этой поставки backend Stage 4 содержит **минимальную совместимую поправку** к DTO `OrderVersionLineView`: новые поля `productId`, `lineNo`. Это позволяет редактировать исходную/отклонённую версию заказа без неоднозначного восстановления товара по названию. HTTP-маршруты и бизнес-логика backend не менялись; сохранены 97 операций. Обязательно используйте совместимый backend-архив из этого выпуска либо внесите эти два поля в прежнюю Stage 4 версию вручную. Изменение обратно совместимо для других клиентов, использующих JSON.

## Запуск на локальном компьютере

Требования: Node.js с поддержкой Vite 8, npm, запущенный backend Stage 4 и PostgreSQL.

1. Распакуйте оба архива. Сначала запустите backend по его README, включая генерацию локальной RSA-пары, настройку БД и bootstrap-администратора.
2. В каталоге frontend выполните:

```bash
npm install
npm run check
npm run build
npm run test:offline
npm run dev
```

3. Откройте `http://localhost:5173`, выполните вход bootstrap-администратором и создайте закупочные учётные записи. Vite проксирует `/api` на `http://localhost:8081`; CORS при этом не нужен.
4. Если backend расположен на другом хосте, задайте публичную `VITE_API_BASE_URL=https://<host>/api/v1`, обеспечьте HTTPS и разрешённый CORS.

**Установка зависимостей в окружении, где был подготовлен этот выпуск, заблокирована сетью (npm registry).** Поэтому `npm run check`, настоящая Vite-сборка и открытие React-приложения в браузере ещё не выполнены. `package-lock.json` здесь не создавался; его следует получить при первом успешном `npm install` и затем сохранить в репозитории.

## Проверки

```bash
npm run test:offline        # Статическая матрица 97/97 + OpenAPI + DTO + HTTP-клиент (без npm-пакетов, нужен TypeScript)
npm run test:contracts      # Матрица 97/97 и чистые builders
npm run test:http-client    # Клиент: JWT, refresh, 401/403, конкурентные запросы
```

Выполнение сквозного API-теста с настоящей БД (он **изменяет данные**, использовать исключительно тестовую БД):

```bash
SMOKE_ADMIN_LOGIN=admin \
SMOKE_ADMIN_PASSWORD='<пароль_из_настроек_backend>' \
SMOKE_API_BASE=http://localhost:8081/api/v1 \
node tools/live-smoke.mjs
```

Этот smoke-тест покрывает значительную часть реального рабочего маршрута, но **не все 97 операций** и не автоматизирует клики по интерфейсу браузера. После него пройдите ручной чек-лист `docs/INTEGRATION_ACCEPTANCE.md`; backend следует также проверять `mvn clean verify` в окружении Docker/Testcontainers.

## Замечания по безопасности

- Access-token хранится в памяти, refresh-token — в `sessionStorage` согласно JSON-контракту Stage 4. В реальном публичном production развёртывании предпочтительна согласованная с backend HttpOnly/Secure cookie-схема и строгая CSP.
- Не сохраняйте секреты и пароли в переменных VITE_: они попадут в JS-бандл.
- UI скрывает недоступные действия ради UX; настоящая проверка ролей и самосогласования производится backend.
- Приложение не претендует на эксплуатационную готовность до успешной реальной Maven/Vite/DB/browser приёмки.

## Структура

`src/core/` — API, auth, типы, справочники и построители запросов; `src/ui/` — дизайн-компоненты; `src/pages/` — экраны реестров, карточек, форм и процессов; `tools/` — проверки контрактов и live smoke; `docs/` — OpenAPI, матрица маршрутов и отчёт.
