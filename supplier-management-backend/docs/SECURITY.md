# Политика безопасности (Stage 4)

Система использует bearer JWT RS256, issuer `supplier-management`, audience `supplier-management`, `token_use=access`, `sub` UUID и `sid` UUID серверной сессии. Access TTL 15 минут. Подписывающая RSA 3072-битная пара хранится вне Git (`secrets/` либо переменные окружения, указывающие путь к PEM).

Refresh-токены — секретные, случайные 256-битные строки. В БД — только SHA-256; токен содержит идентификатор сессии и случайный компонент. При refresh текущий хеш сравнивается в постоянном времени, сессия блокируется на время транзакции и заменяется новым токеном; повтор старого токена отзывает сессию. Абсолютный срок сессии 7 дней. Состояние пользователя, список ролей и действительность сессии повторно читаются при **каждом HTTP-запросе**.

Администратор создаётся однократно при старте из `BOOTSTRAP_ADMIN_*`. Публичного API регистрации нет. Администратор создаёт новых пользователей, назначает/отзывает роли, блокирует/разблокирует, сбрасывает пароль. Сброс/смена пароля и блокировка отзывают все сессии. Самостоятельное изменение собственных ролей запрещено.

При пяти неудачных входах устанавливается блокировка на 15 минут. Неизвестные логины проверяются через фиктивный BCrypt-хеш, чтобы уменьшить утечки по времени. Обработка ошибок не раскрывает SQL/токены/хеши.

**Важно для клиента React:** refresh-токен передаётся JSON, не через cookie. Не храните токены в URL и `localStorage`. Хранение в памяти снижает риски длительного компрометирования; после перезагрузки возможен повторный вход. Для публичного развёртывания обязательно HTTPS, менеджер секретов, мониторинг безопасности и ограничения частоты запросов у reverse proxy.

**Проверка здесь ограниченная:** исходники и проверки компилировались с заглушками; реальное поведение Spring Security проверяется только при исполнении Maven/Testcontainers тестов.
