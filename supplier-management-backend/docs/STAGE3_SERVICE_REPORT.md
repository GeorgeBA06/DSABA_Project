# Отчёт этапа 3 — реализация сервисного слоя

Дата: 31 октября 2026 года. Основа: утверждённая схема из 30 таблиц (`docs/APPROVED_DATA_MODEL.md`) и JPA Entity Stage 2.

## 1. Итоги разработки

- **Схема не расширялась:** 30 PostgreSQL таблиц, 30 JPA Entity и 30 `JpaRepository`.
- Реализовано 19 Java-классов сервисного/политического слоя (`service/`), в том числе 4 бизнес-критерия через полиморфную `CriterionStrategy` и один общий арифметический `RatingPolicy`.
- 16 репозиториев расширены типизированными finder-методами и блокировками; дополнительные finder-методы добавлены для корректировок/учётных записей.
- Код разделён по утверждённым слоям: `entity`, `repository`, `service`; REST-контроллеры и DTO ещё не создавались.
- Исторический SQL V1 оставлен для **чистой** PostgreSQL БД; старые 43-table миграции применять поверх новой нельзя.

## 2. Инварианты и действия

| Сценарий | Реализовано в сервисах | Ограничение/незавершённость |
|---|---|---|
| Специалист работает с любым поставщиком | Да | Без назначения поставщика |
| Смена статуса поставщика | Заявка + решение | Независимость автора/руководителя |
| Версия договора | Черновик → согласование → новая версия | История не перезаписывается |
| Заказ с товарами и договором | Создание, изменение черновика, одобрение | Договор и поставщик проверяются |
| Отклонение первой версии | Переработка через новую историю | Состав товарных строк пока должен совпадать |
| Увеличение заказа | Новый сегмент количества и срока | Уменьшение пока не реализовано |
| Перенос поставщиком | Меняется срок исполнения | Рейтинговый срок сохраняется |
| Поступление | Черновик и подтверждение | Излишек физически сохраняется |
| Приёмка | Частичная, нескольких документов | Сумма проверенного ≤ доставленного; принято ≤ обязательства |
| Возврат | Заявка, одобрение, суммарная проверка | Возврат сверх принятого запрещён |
| Закрытие заказа | Полное / с остатком и снимок по строкам | Нельзя закрыть с непроверенным товаром/открытой коррекцией/возвратом |
| Исправление факта | Новая версия поступления или приёмки | Не полный пакетный сценарий и не исправление возврата |
| Претензии и коммуникации | Состояния, взаимодействия и исход | Частичный/отрицательный исход требует руководителя |
| Экспертная оценка | 0/25/50/75/100; 30 дней | Требуется независимый руководитель |
| Рейтинг | Окно 90 дней, четыре критерия и веса | Текущая дата, вручную вызываемый сервис |
| Ролевой доступ | Проверка действующих назначений и блокировок | JWT/логин/refresh ещё не реализованы |

Критерии рейтинга: своевременность **35%**, полнота **25%**, качество **30%**, экспертное взаимодействие **10%**. Публикация возможна только при достаточной выборке (≥3 заказа), утверждённой применимой экспертной оценке, завершённой проверке поступлений и наличии всех четырёх показателей. При неполных исходных данных общий балл не публикуется и отсутствующие значения не становятся нулевыми.

Сервис расчёта используется на **текущую дату**, а не для произвольного восстановления БД в прошлом. Сохранённые результаты и входные показатели неизменяемы, новый запуск создаёт новую запись. Фоновая ежедневная задача будет добавлена на отдельном этапе.

## 3. Структура и границы транзакций

- `ActorAccess` проверяет активность учётной записи и действующую роль с получением пользователя из БД. На каждое критическое решение действует запрет самосогласования.
- Сервисы отмечены `@Transactional`, а редактируемые корни документов берутся через `@Lock(PESSIMISTIC_WRITE)` для предотвращения гонок при подтверждении и возврате.
- `FulfillmentLedger` читает только подтверждённые действующие факты, исключает версии, замещённые подтверждённым исправлением.
- `AuditTrail` сохраняет бизнес- или security-события в той же транзакции; секреты в аудит не записываются.
- `OrderClosure` и `RatingLineInput` сохраняются как неизменяемые снимки.
- Репозитории возвращают типизированные сущности, но **не должны возвращаться напрямую из будущих REST-контроллеров**; необходим DTO слой.

1. В доступном окружении установить Java 21, Maven 3.9+ и Docker, выполнить `mvn clean verify`; исправить реальные ошибки миграций и mapping.
2. Добавить интеграционные тесты конкурентных приёмок/возвратов и согласований; протестировать корневые блокировки и истории.
3. Реализовать модуль безопасности (bcrypt/Argon2, JWT, refresh, logout), административное создание пользователей.
4. Создать request/response DTO, мапперы, контроллеры, OpenAPI и стандартизованную обработку ошибок.
5. Завершить оставшиеся минимально необходимые бизнес-операции, реализовать автоматический ежедневный рейтинг, аналитические запросы и XLSX отчёты; интегрировать frontend.

Сохраняем согласованный визуальный стиль интерфейса; пересмотр общей концепции не нужен.
